# RNA-seq Managed Agents

Multi-agent orchestration for differential gene expression pipeline monitoring, built around GenPipes RNA-seq Light (C3G, McGill). Agents are coordinated using Anthropic's Managed Agents framework.

**Author:** Joshua Virani-Wall
**Contact:** joshuajamesvw@gmail.com

---

## Project Overview

This project investigates how variation in wetlab protocol — RNA extraction method, library fragmentation, and sequencing platform — propagates into systematic gene expression differences. It uses publicly available ENCODE RNA-seq data from the GM12878 human cell line, where the same biological sample was independently processed by two labs using distinct protocols (Gingeras/CSHL and Wold/Caltech).

## GenPipes Setup

GenPipes runs inside a Docker container provided by C3G. This allows the full pipeline to run locally on your machine without a cluster.

### Prerequisites

Install Docker Desktop and macFUSE via Homebrew:

```bash
brew install --cask docker
brew install --cask macfuse
```

After installing macFUSE, go to **System Settings → Privacy & Security** and allow the kernel extension from Benjamin Fleischer.

### CVMFS Cache

Create a local cache folder for reference genomes and bioinformatics tools (this will grow over time):

```bash
mkdir -p ~/genpipes-cvmfs-cache
```

### Launch the GenPipes Container

From your project folder, run:

```bash
cd ~/Projects/rnaseq_managed-agents

docker run --rm \
  --device /dev/fuse \
  --cap-add SYS_ADMIN \
  -v /tmp:/tmp \
  -it \
  -w $PWD \
  -v $HOME:$HOME \
  -v ~/genpipes-cvmfs-cache:/cvmfs-cache/ \
  ghcr.io/c3g/genpipes_in_a_container:latest
```

This mounts your project folder and home directory into the container. Reference genomes and tools are streamed on demand via CVMFS and cached in `~/genpipes-cvmfs-cache`.

## Agent Workflow

The full agent workflow covers two phases: pipeline preparation (generating the input files GenPipes needs) and pipeline monitoring (checking the quality of each step's output and deciding whether the pipeline can continue).

### Architecture

```
setup.py                              ← run once: registers all agents with Anthropic
agents/
  readset_agent.py                    ← generates readset.tsv
  design_agent.py                     ← generates design.tsv
  trimmomatic_monitor_agent.py        ← monitors Trimmomatic output, writes qc_report.xml
  kallisto_monitor_agent.py           ← monitors Kallisto output, appends to qc_report.xml
generate_readset.py                   ← session runner for readset agent
generate_design.py                    ← session runner for design agent
# monitor_trimmomatic.py              ← session runner for Trimmomatic monitor (not yet connected)
# monitor_kallisto.py                 ← session runner for Kallisto monitor (not yet connected)
agent_config.json                     ← written by setup.py, read by all session runners
qc_report.xml                         ← accumulated QC findings, written during pipeline run
```

`setup.py` creates persistent agent definitions on Anthropic's servers and saves their IDs to `agent_config.json`. Session runners open a conversation with the relevant agent, pass the required inputs, and receive the output.

### Phase 1 — Pipeline Preparation

These agents are fully implemented and operational. They generate the input files GenPipes RNA-seq Light requires before the pipeline can run.

#### Step 1 — Register agents

Run once. Re-run only if `agent_config.json` is deleted or you want to update an agent definition.

```bash
conda activate managed-agents
python setup.py
```

Expected output:

```
  Agent ID: agent_...

Creating agent: rnaseq-design-generator...
  Agent ID: agent_...

Creating agent: rnaseq-trimmomatic-monitor...
  Agent ID: agent_...

Creating agent: rnaseq-kallisto-monitor...

```

#### Step 2 — Generate the readset file

Point the script at your FASTQ directory and metadata files. Use `--include _3M` to restrict to subsampled files for local development, or `--exclude _3M` to use full files.

```bash
python generate_readset.py \
  --fastq-dir ~/Projects/rnaseq_managed-agents \
  --metadata ~/Projects/rnaseq_managed-agents/gingeras_cshl/metadata/ENCSR000AED.json \
             ~/Projects/rnaseq_managed-agents/wold_caltech/metadata/ENCSR000AEG.json \
  --include _3M \
  --output readset.tsv
```

The agent will:
1. Scan and pair FASTQ files
2. Extract adapter sequences and replicate information from metadata
3. Print an inference report showing what it determined and what it assumed
4. Ask clarifying questions about anything it could not determine
5. Output the finished readset TSV

Answer any questions at the `YOU >` prompt. The session ends automatically when the readset file is written to disk.

#### Step 3 — Verify the readset

```bash
cat readset.tsv
```

Expected: a tab-separated file with one header row and four data rows (one per replicate), 13 columns each.

You can also validate it using GenPipes' built-in validator inside the Docker container:

```bash
python mugqicValidator.py -r readset.tsv
```

#### Step 4 — A note on Sample naming

Before generating the design file, it is worth understanding how the `Sample` field is used in this pipeline.

Biologically, a sample is the original tissue or cell line — in this project, that is GM12878 for all four readsets. GenPipes RNA-seq Light (Kallisto + Sleuth) however treats `Sample` as the **unit of differential expression**: Kallisto runs per readset, then aggregates all readsets sharing the same Sample name into a single quantification before Sleuth compares groups.

This means the `Sample` field in the readset must be defined at the level you want to compare, not at the level of the original biological source. Here, we want to compare the Gingeras protocol against the Wold protocol, so Sample was defined as the experiment:

| Sample | Readset |
|---|---|
| GM12878_Gingeras | ENCFF001REI |
| GM12878_Gingeras | ENCFF001REK |
| GM12878_Wold | ENCFF001RVY |
| GM12878_Wold | ENCFF001RVS |

The two Gingeras readsets (biological replicates) are aggregated by Kallisto into a single `GM12878_Gingeras` quantification. Sleuth then tests for differential expression between `GM12878_Gingeras` and `GM12878_Wold`. The replicates inform the variance estimate within each group, not separate rows in the design file.

The design agent will ask you how to define Sample before generating the readset. For this dataset the answer is: one Sample per experiment, with both replicates sharing that Sample name.

#### Step 5 — Generate the design file

```bash
python generate_design.py \
  --readset ~/Projects/rnaseq_managed-agents/readset.tsv \
  --output ~/Projects/rnaseq_managed-agents/design.tsv
```

The agent will:
1. Parse the readset TSV and display the unique Sample names it found
2. Ask you to name each contrast (e.g. `Gingeras_vs_Wold`)
3. Ask which samples are control (`1`), which are treatment (`2`), and which are excluded (`0`)
4. Confirm the mapping before generating output
5. Output the finished design TSV

For this dataset, the session looks like:

```
AGENT > I found 2 unique samples: GM12878_Gingeras, GM12878_Wold.
        What would you like to name this contrast?
YOU   > Gingeras_vs_Wold
AGENT > Which sample is the control (1) and which is the treatment (2)?
YOU   > GM12878_Gingeras is control, GM12878_Wold is treatment
```

Expected output (`design.tsv`):

```
Sample              Gingeras_vs_Wold
GM12878_Gingeras    1
GM12878_Wold        2
```

#### Step 6 — Verify the design file

```bash
cat design.tsv
```

Expected: a tab-separated file with one header row and two data rows (one per sample), with `1` and `2` in the contrast column.

### Phase 2 — Pipeline Monitoring

These agents monitor the GenPipes RNA-seq Light pipeline as it runs, applying QC decision rules after each major step and either clearing the pipeline to continue or halting it for investigation. Their agent definitions are complete and registered with Anthropic, but they are not yet connected to live pipeline output. See [Current Limitations](#current-limitations) for why.

#### How monitoring works

Each monitor agent follows the same pattern: it reads the output files produced by a pipeline step, applies a set of decision rules, and returns either **GO** or **NO-GO**. It cannot modify the pipeline or rerun steps — it only reads, assesses, and decides.

Every assessment is appended as a structured XML block to a shared file called `qc_report.xml`. This file accumulates findings across the entire run, so by the end you have a complete audit trail of what every step found. Crucially, each agent reads the findings from previous steps before making its own assessment — so a pattern that spans two steps (such as borderline-low adapter survival followed by borderline-low pseudoalignment) is detected and documented as a coherent picture, not two unrelated observations.

#### Trimmomatic monitor

Called after Trimmomatic finishes adapter trimming across all readsets. Reads the GenPipes job stderr log for each readset, which contains the Trimmomatic summary line:

```
Input Read Pairs: N  Both Surviving: N (X%)  Forward Only Surviving: N (X%)  Reverse Only Surviving: N (X%)  Dropped: N (X%)
```

The primary metric is the **both-surviving percentage** — the fraction of read pairs where both R1 and R2 survived all trimming filters. These are the reads passed to Kallisto.

Decision rules applied per readset:

| Survival rate | Outcome |
|---|---|
| Below 70% | FAIL → NO-GO. Wrong adapters or severely degraded RNA. |
| 70–75% | PASS + yellow flag (borderline low) |
| 75–95% | PASS |
| 95–99% | PASS + yellow flag (borderline high) |
| Above 99% | WARN → NO-GO. Almost nothing trimmed; adapters likely didn't match. |

Additionally, if readsets from the same biological sample differ by more than 15 percentage points in survival rate, a variance yellow flag is recorded. This does not block the pipeline but indicates inconsistent library quality across replicates.

All findings — including yellow flags — are written to `qc_report.xml` as the first `<step_assessment>` block.

#### Kallisto monitor

Called after Kallisto finishes pseudoalignment across all samples. In GenPipes 6.x, Kallisto aggregates readsets by sample before running, so output is one directory per sample rather than per readset.

Reads two files per sample:

- **`run_info.json`** — run-level statistics including the pseudoalignment rate (`p_pseudoaligned`). This drives the go/no-go decision.
- **`abundance.tsv`** — per-transcript estimated counts (`est_counts`) and TPM values. The agent computes summary statistics from this file rather than reading every row: total TPM (integrity check), fraction of transcripts with zero counts, and whether any single transcript dominates the library (a signal for rRNA contamination).

The primary metric is **p_pseudoaligned** — the percentage of reads that mapped to at least one transcript in the reference index.

Decision rules applied per sample:

| Pseudoalignment rate | Outcome |
|---|---|
| Below 50% | FAIL → NO-GO. Almost certainly a wrong or mismatched index. |
| 50–60% | WARN → NO-GO. Likely a real problem — investigate before continuing. |
| 60–70% | PASS + yellow flag (borderline low) |
| 70–90% | PASS |
| Above 90% | PASS + yellow flag (borderline high) |

Before applying these rules, the agent reads `qc_report.xml` and looks up the Trimmomatic findings for each sample. Two cross-step patterns carry additional diagnostic weight:

- **Dual high**: Trimmomatic borderline-high or WARN combined with Kallisto above 90%. Both elevated numbers together suggest adapter sequences are pseudoaligning to the transcriptome index, inflating both metrics.
- **Dual low**: Trimmomatic borderline-low combined with Kallisto 60–70%. Consistent with degraded input RNA at both steps. If both are present, the borderline Kallisto rate is upgraded to WARN and the pipeline stops.

The agent also checks that Kallisto's `n_processed` approximately matches the sum of Trimmomatic's `both_surviving` counts for all readsets belonging to that sample. A large discrepancy means reads were lost between steps.

All findings are appended to `qc_report.xml` as a second `<step_assessment>` block, producing a complete two-step QC record for the run.

#### What the QC report looks like

After both monitors have run, `qc_report.xml` contains a structured record of every finding:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<qc_report>

  <step_assessment step="trimmomatic" timestamp="2024-06-01T14:23:11" decision="GO">
    <readsets>
      <readset name="ENCFF001REK">
        <metric name="survival_rate_pct" value="91.0"/>
        <status value="PASS"/>
        <note></note>
      </readset>
      ...
    </readsets>
    <decision value="GO"/>
    <reason>All four readsets passed with survival rates between 88% and 93%.</reason>
  </step_assessment>

  <step_assessment step="kallisto" timestamp="2024-06-01T15:47:03" decision="GO">
    <samples>
      <sample name="GM12878_Gingeras">
        <metric name="p_pseudoaligned" value="84.1"/>
        <status value="PASS"/>
        <note></note>
      </sample>
      ...
    </samples>
    <decision value="GO"/>
    <reason>Both samples passed with pseudoalignment rates of 84% and 81%.</reason>
  </step_assessment>

</qc_report>
```

## Current Limitations

**GenPipes cannot currently run on this machine.** The pipeline requires a human reference transcriptome and a C3G-formatted transcript-to-gene mapping file. Both are distributed via CVMFS — a network filesystem that the GenPipes container streams on demand. On macOS, CVMFS requires macFUSE, which in turn requires a kernel extension. Docker Desktop on Mac does not support kernel extensions inside containers, which means CVMFS cannot mount inside the GenPipes container. As a result, the reference data needed to run Trimmomatic and Kallisto is inaccessible.

This is a known limitation of running GenPipes locally on Apple Silicon Macs. The C3G team has been contacted and may be able to provide an alternative approach — either a pre-built container with the reference data bundled, or access to a remote compute environment. This limitation will be revisited as that conversation develops.

**The monitor agents are built but not yet connected.** `trimmomatic_monitor_agent.py` and `kallisto_monitor_agent.py` are complete agent definitions with full system prompts, decision rules, and QC report format specifications. They are registered with Anthropic via `setup.py` and their IDs are saved to `agent_config.json`. The session runners that would call them during a live pipeline run (`monitor_trimmomatic.py`, `monitor_kallisto.py`) have not yet been written, because there is no live pipeline output to connect them to. Once GenPipes can run, writing the session runners is straightforward — the agent definitions are the harder part, and they are done.

**The monitor agents' decision rules will be refined with experience.** The QC thresholds in the current monitor agents — survival rate bands for Trimmomatic, pseudoalignment rate bands for Kallisto — are based on published best practices and general bioinformatics experience. They have not yet been validated against real run data from this specific dataset or pipeline configuration. Both agents will be substantially revised after attending the OICR Canadian Bioinformatics Workshop on RNA-seq analysis in June 2026, which will provide hands-on experience with interpreting these metrics on real data.

**Managed Agents beta instability.** The streaming API (`client.beta.sessions.events.stream`) drops connections intermittently. The current implementation uses a polling fallback (`client.beta.sessions.events.list`) which is more reliable but less elegant. This will be revisited when the API stabilises out of beta.

**seen_event_ids must persist across turns.** The polling loop deduplicates events using a `seen_event_ids` set. This set must be created once per session and passed into every `stream_agent_response` call — if it resets between turns, old events are replayed and the agent appears to loop. Both `generate_readset.py` and `generate_design.py` implement this correctly.

**Large metadata files.** ENCODE experiment JSONs can exceed 900 KB. The `files` key — which contains download URLs for all processed files — accounts for the bulk of this and is stripped before sending to the agent. The agent does not need file download URLs since FASTQ paths are provided directly from the directory scan.

**Run and Lane fields.** ENCODE metadata for this dataset does not contain flowcell or lane identifiers. Run is set to `1` and Lane to `0` as placeholders. GenPipes does not appear to enforce uniqueness on these fields but this has not been formally verified.

**Gingeras replicate assignment.** The agent infers which FASTQ pair belongs to replicate 1 vs replicate 2 from ENCODE accession order (earlier accession = earlier submission = replicate 1). This assumption has not been independently verified against the original ENCODE submission records.
