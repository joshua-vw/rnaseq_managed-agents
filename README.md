# RNA-seq Managed Agents

Multi-agent orchestration for differential gene expression pipeline monitoring, built around GenPipes RNA-seq Light (C3G, McGill). Agents are coordinated using Anthropic's Managed Agents framework.

**Author:** Joshua Virani-Wall
**Contact:** joshuajamesvw@gmail.com

---

## Project Overview

This project investigates how variation in wetlab protocol — RNA extraction method, library fragmentation, and sequencing platform — propagates into systematic gene expression differences. It uses publicly available ENCODE RNA-seq data from the GM12878 human cell line, where the same biological sample was independently processed by two labs using distinct protocols (Gingeras/CSHL and Wold/Caltech).

## GenPipes Setup

GenPipes runs inside a Docker container provided by C3G. This allows the full pipeline to run locally on your machine without a cluster.

### Prerequisites

Install Docker Desktop and macFUSE via Homebrew:

```bash
brew install --cask docker
brew install --cask macfuse
```

After installing macFUSE, go to **System Settings → Privacy & Security** and allow the kernel extension from Benjamin Fleischer.

### CVMFS Cache

Create a local cache folder for reference genomes and bioinformatics tools (this will grow over time):

```bash
mkdir -p ~/genpipes-cvmfs-cache
```

### Launch the GenPipes Container

From your project folder, run:

```bash
cd ~/Projects/rnaseq_managed-agents

docker run --rm \
  --device /dev/fuse \
  --cap-add SYS_ADMIN \
  -v /tmp:/tmp \
  -it \
  -w $PWD \
  -v $HOME:$HOME \
  -v ~/genpipes-cvmfs-cache:/cvmfs-cache/ \
  ghcr.io/c3g/genpipes_in_a_container:latest
```

This mounts your project folder and home directory into the container. Reference genomes and tools are streamed on demand via CVMFS and cached in `~/genpipes-cvmfs-cache`.

## Agent Workflow

The agent workflow generates the three input files GenPipes RNA-seq Light requires: a readset file, a design file, and INI config files. Each is produced by a dedicated agent.

### Architecture

```
setup.py                  ← run once: registers all agents with Anthropic
agents/
  readset_agent.py        ← system prompt and config for readset agent
  design_agent.py         ← system prompt and config for design agent
  # monitor_agent.py      ← coming soon
generate_readset.py       ← session runner: talks to readset agent interactively
generate_design.py        ← session runner: talks to design agent interactively
agent_config.json         ← written by setup.py, read by session runners
```

`setup.py` creates persistent agent definitions on Anthropic's servers and saves their IDs to `agent_config.json`. Session runners (`generate_readset.py`, `generate_design.py`) open a conversation with the relevant agent, send the required inputs, and receive the output file.

### Step 1 — Register agents

Run once. Re-run only if `agent_config.json` is deleted or you want to update an agent definition.

```bash
conda activate managed-agents
python setup.py
```

Expected output:
```
Creating Environment...
  Environment ID: env_...

Creating agent: rnaseq-readset-generator...
  Agent ID: agent_...

Creating agent: rnaseq-design-generator...
  Agent ID: agent_...

Config written to /path/to/agent_config.json
Done.
```

### Step 2 — Generate the readset file

Point the script at your FASTQ directory and metadata files. Use `--include _3M` to restrict to subsampled files for local development, or `--exclude _3M` to use full files.

```bash
python generate_readset.py \
  --fastq-dir ~/Projects/rnaseq_managed-agents \
  --metadata ~/Projects/rnaseq_managed-agents/gingeras_cshl/metadata/ENCSR000AED.json \
             ~/Projects/rnaseq_managed-agents/wold_caltech/metadata/ENCSR000AEG.json \
  --include _3M \
  --output readset.tsv
```

The agent will:
1. Scan and pair FASTQ files
2. Extract adapter sequences and replicate information from metadata
3. Print an inference report showing what it determined and what it assumed
4. Ask clarifying questions about anything it could not determine
5. Output the finished readset TSV

Answer any questions at the `YOU >` prompt. The session ends automatically when the readset file is written to disk.

### Step 3 — Verify the readset

```bash
cat readset.tsv
```

Expected: a tab-separated file with one header row and four data rows (one per replicate), 13 columns each.

You can also validate it using GenPipes' built-in validator inside the Docker container:

```bash
python mugqicValidator.py -r readset.tsv
```

### Step 4 — A note on Sample naming

Before generating the design file, it is worth understanding how the `Sample` field is used in this pipeline.

Biologically, a sample is the original tissue or cell line — in this project, that is GM12878 for all four readsets. GenPipes RNA-seq Light (Kallisto + Sleuth) however treats `Sample` as the **unit of differential expression**: Kallisto runs per readset, then aggregates all readsets sharing the same Sample name into a single quantification before Sleuth compares groups.

This means the `Sample` field in the readset must be defined at the level you want to compare, not at the level of the original biological source. Here, we want to compare the Gingeras protocol against the Wold protocol, so Sample was defined as the experiment:

| Sample | Readset |
|---|---|
| GM12878_Gingeras | ENCFF001REI |
| GM12878_Gingeras | ENCFF001REK |
| GM12878_Wold | ENCFF001RVY |
| GM12878_Wold | ENCFF001RVS |

The two Gingeras readsets (biological replicates) are aggregated by Kallisto into a single `GM12878_Gingeras` quantification. Sleuth then tests for differential expression between `GM12878_Gingeras` and `GM12878_Wold`. The replicates inform the variance estimate within each group, not separate rows in the design file.

The design agent will ask you how to define Sample before generating the readset. For this dataset the answer is: one Sample per experiment, with both replicates sharing that Sample name.

### Step 5 — Generate the design file

```bash
python generate_design.py \
  --readset ~/Projects/rnaseq_managed-agents/readset.tsv \
  --output ~/Projects/rnaseq_managed-agents/design.tsv
```

The agent will:
1. Parse the readset TSV and display the unique Sample names it found
2. Ask you to name each contrast (e.g. `Gingeras_vs_Wold`)
3. Ask which samples are control (`1`), which are treatment (`2`), and which are excluded (`0`)
4. Confirm the mapping before generating output
5. Output the finished design TSV

For this dataset, the session looks like:

```
AGENT > I found 2 unique samples: GM12878_Gingeras, GM12878_Wold.
        What would you like to name this contrast?
YOU   > Gingeras_vs_Wold
AGENT > Which sample is the control (1) and which is the treatment (2)?
YOU   > GM12878_Gingeras is control, GM12878_Wold is treatment
```

Expected output (`design.tsv`):

```
Sample              Gingeras_vs_Wold
GM12878_Gingeras    1
GM12878_Wold        2
```

### Step 6 — Verify the design file

```bash
cat design.tsv
```

Expected: a tab-separated file with one header row and two data rows (one per sample), with `1` and `2` in the contrast column.

## Known Limitations

**Managed Agents beta instability.** The streaming API (`client.beta.sessions.events.stream`) drops connections intermittently. The current implementation uses a polling fallback (`client.beta.sessions.events.list`) which is more reliable but less elegant. This will be revisited when the API stabilises out of beta.

**seen_event_ids must persist across turns.** The polling loop deduplicates events using a `seen_event_ids` set. This set must be created once per session and passed into every `stream_agent_response` call — if it resets between turns, old events are replayed and the agent appears to loop. Both `generate_readset.py` and `generate_design.py` implement this correctly.

**Large metadata files.** ENCODE experiment JSONs can exceed 900 KB. The `files` key — which contains download URLs for all processed files — accounts for the bulk of this and is stripped before sending to the agent. The agent does not need file download URLs since FASTQ paths are provided directly from the directory scan.

**Run and Lane fields.** ENCODE metadata for this dataset does not contain flowcell or lane identifiers. Run is set to `1` and Lane to `0` as placeholders. GenPipes does not appear to enforce uniqueness on these fields but this has not been formally verified.

**Gingeras replicate assignment.** The agent infers which FASTQ pair belongs to replicate 1 vs replicate 2 from ENCODE accession order (earlier accession = earlier submission = replicate 1). This assumption has not been independently verified against the original ENCODE submission records.
